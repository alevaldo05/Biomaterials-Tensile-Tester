# Tester app: what works, what is simulated, what is untested, what is unsupported

Updated with each stage. "Checked" means tried in Chrome's engine (Chromium on Linux) only; Safari and a real Windows computer have not been tried.

## Implemented and checked

- Home ("Split with tiles"), menu, six separate status indicators, Need help on every screen (help words in `apps/tester/src/help-text.ts`, offline), searchable Help.
- The Test screen in one window (the approved "Version C" layout): a Quick settings panel (Test, Specimen, Connection, Setup file and calibration, Before you start) that folds to a slim rail while recording and after the test, and is a Setup drawer at 1100 px and narrower; the graph with its view switch, data-source tag, and action bar (Zero force, Start / End recording, Save data, New test, and the line that the app only records); live readouts or key results on the right (under the graph at 768 px and narrower); and a Specimens strip of the tests finished since the app was opened. Key results and axis titles carry no equations; each result has an "i" button with its definition and caveats. The CSV, Excel, and report keep their full wording. Checked in Chromium only, with the stand-in test device in a throwaway harness (not a real board): setup, recording, and results at 1366, 1024, 768, and 390 px in light and dark, no console errors, no sideways page scroll, no overlapping controls, focus visible on every Tab stop, the drawer returning focus to Setup, the Save data menu closing on Tab, a click outside, and Esc, and the print report. The other screens (Home, Load test, Device, Help, Settings) only got the new header and were checked for errors and sideways scroll; they are restyled in a later pass. Not tried in Safari, on Windows, or in the Windows app.
- Connecting again: after a fault or a device restart the Test and Device screens offer both Disconnect and Connect; Connect closes the old connection first (sending nothing to the device), so the same USB port can be opened again. A finished test keeps its own session file through a new Connect or a Disconnect. Checked with a stand-in port that, like Web Serial, refuses a second open; not with a real board.
- Real acquisition only. The simulator is used only by the automated tests, as a stand-in device; a test checks that the app's source does not import it, and the built app does not contain it.
- Recordings kept on this computer (the browser's IndexedDB) while recording, committed about once a second; an interrupted recording is offered for recovery on Home. Checked in the automated tests (commits, a failed write, recovery) with an in-memory store; the real IndexedDB store (`IdbJournal`) was tried once in Chromium 153 on Linux with a stand-in recording of 5 minutes at 100 Hz (300 one-second batches, 60,000 lines): commit, line order across batches, the sample count, recovery after a page reload (still listed as recording, every line back), a refused write (a value the browser cannot store, which rejects and leaves the stored lines unchanged), finish, and remove. That check was a one-time script, not an automated test, and it did not try a full disk, the database upgrade, Safari, or the Windows app. It has not been tried with a real recording from a board.
- Load test: session files (rebuilt from their lines, sending nothing to any device) and CSV files; files marked simulated or sample are refused; imports are labeled as unverified. Print report (Draft, light colors on paper; also in Save data after a test) was checked with Chromium's print preview on Load test only; after a test it has not been tried, since that needs a connected device.
- Graph guides after a test (display only): region guides on the stress view (from the shared `regionsFor`) and a tangent line at the cursor whose slope is a least-squares fit over nearby points (about 1% of the record each side), shown in the readout. Tried in Chromium.
- Calibration check with known weights (Device screen): typed readings, or the device's calibrated force averaged over 1 s with Read force; per-point errors, tolerance flags, fitted line, CSV, Copy, Print. Changes no calibration. Read force has not been tried with a real device.
- Compare tests (on Load test): up to 12 tests of one type, overlay graph, key results with mean and sample SD, warnings, summary CSV (text cells formula-guarded like the other CSV files). The material and specimen ID of a CSV file come from its header lines, so the mixed-materials and specimen ID warnings work for CSV files too. The summary is covered by automated tests; the screen was tried in Chromium only.
- Test methods: saved setups with revisions, kept on this computer, and shared through the lab server when signed in (admins save, change, and archive; everyone signed in can start a test from one). Checked against a real PostgreSQL 16 in the API tests and in the browser with the API running.
- Recording: every sample with counts, device time, computer time, settings, volts, and the calibrated value; gaps, faults, restarts, and disconnects are written into the session. The session file keeps a fault, restart (hello), or settings line sent while recording in its place among the samples, and says how the recording ended (`interrupted`, `endReason`, `events`); a test ended by a fault, restart, or lost connection reopens in Load test and from the journal as interrupted, and the journal entry is marked interrupted with the reason. Received lines are sorted by the message type read from them, so a device that writes JSON with spaces is recorded too.
- Key results from the shared calculations (the same numbers the website gives for the same data). A software baseline taken before Start is saved with the test (`forceZero_N` in the session file and the journal) and applied again in Load test and recovery, so reopened results match the live ones.
- Save data: test CSV (opens on the website's Load Test page), Excel (.xlsx, checked with openpyxl, not Microsoft Excel), graph PNG and SVG, every raw sample as CSV, and a session file for replay.
- Graph: three views, Autoscale, Reset view, Expand, scroll and drag zoom, pan, arrow-key readout, key-result markers with snapping.
- Theme: Light, Dark, or Follow system (the default, which follows the computer's setting while the app is open), chosen in Settings and remembered on this computer; the website's default green only. Text and control borders are checked for contrast in both themes by `apps/tester/test/app-checks.test.ts`. Laptop, tablet, and phone widths (1366, 1280, 1024, 768, 390 px) without sideways scrolling; 1280 was not re-checked after the Test screen layout changed.

## Back end and database

- Implemented and tested against a real PostgreSQL 16: sign-in with argon2id passwords, admin and user roles enforced on the server, saved tests with their full session files, device profiles, calibrations (draft, approved, retired; real equipment only; never overwritten), and a record of changes. See [BACKEND.md](BACKEND.md).
- In the app: Sign in, History (own tests; admins see everyone's), Save to lab database, loading a profile and its approved calibrations in the Calibration step, an Admin page, and View as user.
- Windows steps for the containers (Docker Desktop, line endings kept by `.gitattributes`) are written in [CONTAINERS.md](CONTAINERS.md) but **not yet tried on Windows**. Runs in containers ([CONTAINERS.md](CONTAINERS.md)): built and run with Docker here; each service was stopped, restarted, or replaced while the others kept working, and a backup was restored. Not yet tried on your computer, the lab computer, or Docker Desktop on Windows. A backup service writes a database dump every 24 hours (14 kept), and the gateway serves HTTPS when a certificate is in `deploy/certs` (`deploy/make-cert.sh` makes a self-signed one). Both were run here with Docker and curl; not yet in a browser over HTTPS or on Windows.
- The test image (`deploy/test/Dockerfile`) could not be built in the environment where this was first written (it cannot reach the Debian package mirror), so its steps were run outside a container there. GitHub builds it in the `tests` job of `.github/workflows/app.yml`, which has passed on `main`.
- Replay rehearsal: a stand-in recording is taken through a session file, Load test, the CSV and Excel exports, the report numbers, and a save to the lab server, with a simulated copy refused at each end (`apps/tester/test/rehearsal.test.ts`, `apps/api/test/api.test.ts`). The recording is from the test simulator, so it shows the path works, not that any real tester or board does. The browser's print window is not tested.

## Website and app together

- The website's own live test pages are retired. New Test on the website points to the tester app, the practice page, and Load Test. The website has no USB connection any more.
- The app is not published on GitHub Pages. Get the App on the website says "Download not yet available".
- Windows app (`apps/desktop`, Electron): written and its settings checked by tests, built once by GitHub (the first run of `.github/workflows/desktop.yml` succeeded and made a draft release, `app-v0.2.0-beta.1`), but **never installed or run on a Windows computer** (the first-install checklist in [WINDOWS-APP.md](WINDOWS-APP.md) is not yet filled in). The workflow builds an unsigned beta installer into a draft release when started by hand; code signing is not planned. Its link to the lab server (address in Settings; requests to /api/v1/ sent on by the main process, which holds the sign-in) is tested against the real API without Electron; the Settings box was tried in Chromium with a stand-in for the Windows app. A start-up check of the built program (`apps/desktop/smoke.cjs`) is part of the build and passed on a Windows runner (the program started and showed only its own screen); a failure now stops the build. It does not test USB, recording, or an installed copy. See [WINDOWS-APP.md](WINDOWS-APP.md).
- Windows app version 1 (`1.0.0-beta.1`, written only in `apps/desktop/package.json`; the build gives it to the screens, so session files saved from now on carry it): the workflow now also builds a **portable** `.exe` (unsigned, runs without installing) beside the installer and hashes and attaches both. The portable `.exe` is **untried**: it has not been built by GitHub yet or run on Windows; its electron-builder settings were checked only against electron-builder's settings schema on Linux. Version 1.0.0-beta.1 has not been built on GitHub yet.
- Build stamp: Help ends with "Version <v> · built from <commit> · shared website files <hash>" (`apps/tester/build-info.ts`, `apps/tester/src/version.ts`); the workflow prints the same line in its job summary and release notes. The hash covers the website files the app shares, listed once in `scripts/shared-files.js` (`node scripts/shared-files.js` prints it; line endings are made LF first, so Windows and Linux agree). Drift check: `apps/tester/test/shared-files.test.mjs` fails if the app's build or the reference tests read a website file that is not on the list (a scan of their source and a run with every file read recorded). The Help line was checked in Chromium at 1366 and 390 px (wraps, no sideways scroll); not yet in the Windows app.
- The app uses the website's definitions and materials (read at build time from `data/terms.js` and `data/materials.js`).

## Reference firmware (ESP32 + ADS1115)

- Implemented: shared code in `firmware/common/` (protocol, acquisition loop, ADS1115 driver; no chip calls) and the ESP32 board folder `firmware/esp32-ads1115/` (platformio.ini, board_config.h, and main.cpp with the chip-specific code in one marked block); another board adds its own folder only ([README](../../firmware/README.md)). Protocol v1, the six acquisition requests, ADS1115 single-shot conversions one channel after another, raw counts with a microsecond timestamp each, a new boot id per start and a new settings reference per change, lost-sample counting, achieved rate, ADC faults.
- Checked on a computer only: its protocol, acquisition loop, and ADS1115 driver are compiled with a C++ compiler and run against a pretend ADS1115, both in their own unit tests and with the app's real connection and recorder (`packages/recording/test/firmware.test.ts`).
- A bench record sheet for the first board connection (tester disconnected) is written in [SETUP.md](SETUP.md); it has not been filled in.
- Compiled on GitHub, not in this environment (the PlatformIO toolchain download was blocked here): the `firmware-build` job in `.github/workflows/app.yml` builds every `firmware/*/platformio.ini` (compile only, no upload, no board named in the workflow, so another board needs no workflow change; see "Adding another board" in [SETUP.md](SETUP.md)). The ESP32 build passed with `espressif32` 8.0.0, now pinned in its `platformio.ini`. It is **never run on a board**, the ADS1115 wiring is untried, and the Windows USB drivers are unchecked.

## Simulated

- The app has no simulation source. The website's practice page keeps its own labeled simulator.

## Implemented but untested with real equipment

- USB serial (Web Serial) connection: checked only against a stand-in port in the automated tests. No real board has been connected.
- Real acquisition with a setup file (device profile and calibration records): the loading and the compatibility check are tested with made-up records; no real calibration exists yet.
- The protocol has been spoken by the simulator and by the reference firmware's code on a computer, never by a real board.

## Not built yet

- Pico firmware and a Raspberry Pi service (guides only: [GUIDE-pico.md](GUIDE-pico.md), [GUIDE-raspberry-pi-service.md](GUIDE-raspberry-pi-service.md)).
- A network connection to a Raspberry Pi.
- (Nothing else planned is missing; see "Implemented but untested" above for what still needs real equipment.)

## Unsupported on purpose

- Any control of the tester (start, stop, speed, position, tare on the machine). The app has no such buttons, and the machine-control package answers "unsupported" and transmits nothing.
- An emergency stop. The app has none and does not claim one.

## Unknown, and not assumed anywhere

- The tester's analog output pins, signal scaling, grounding, and any computer-control protocol.
